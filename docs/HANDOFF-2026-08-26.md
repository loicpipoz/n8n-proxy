## Cloudflare et HA n8n

Deux certificats Origin CA distincts sont installes, un par VPS. Le mode SSL de
la zone est `strict`. Ils ne sont pas encore actifs, car le proxy Cloudflare a
renvoye un Managed Challenge aux clients webhook.

Reglages observes :

- `security_level=high` ;
- `browser_check=on` ;
- Bot Fight Mode desactive ;
- une Configuration Rule cible deja `n8n-wh01.spiritviews.com` et desactive
  Browser Integrity Check ainsi que le niveau de securite pour ce hostname ;
- le proxy Cloudflare renvoie encore un Managed Challenge `403` sur les routes
  n8n ;
- le token API est RW sur le compte, mais le plan courant refuse la reecriture
  des Managed Rulesets et des reponses WAF personnalisees historiques.

Le chantier Cloudflare est en pause jusqu'au reabonnement. La Configuration
Rule existante est limitee a :

```text
http.host eq "n8n-wh01.spiritviews.com"
```

Elle met `Security Level` a `Essentially Off` et desactive `Browser Integrity
Check` pour ce hostname uniquement. Apres reabonnement, ajouter l'exception WAF
sur les routes webhook/form, puis tester un client non navigateur avant toute
bascule DNS.

La cible HA est deux enregistrements `A` proxifies pour
`n8n-wh01.spiritviews.com`, vers `84.234.18.145` et `84.234.21.124`. Le simple
multi-origine Cloudflare fournit une reprise basique ; des health checks et un
failover actif/passif exigent Cloudflare Load Balancing.

## Durcissement SP-VPSL-02 du 27 aout 2026

Le VPS a ete redemarre de maniere controlee et fonctionne avec le noyau
`6.12.105+deb13-amd64`.

Le filtrage d'entree local est gere par :

```text
/etc/nftables.d/sp-vpsl-02-input.nft
/etc/systemd/system/spiritviews-input-firewall.service
```

La politique `INPUT` est restrictive. Elle conserve les connexions etablies,
ICMP/ICMPv6, DHCP, les interfaces locales Docker, Tailscale, les ports publics
80/443, RustDesk 21114-21119/TCP et 21116/UDP, ainsi que Tailscale 41641/UDP.
SSH est accessible par `tailscale0`, mais pas par l'interface publique. Le port
Caddy interne 22114 n'est accepte depuis `ens3` que lorsque le port original
avant redirection NAT etait 21114.

L'unite `systemd-networkd-wait-online` utilise l'override persistant :

```text
/etc/systemd/system/systemd-networkd-wait-online.service.d/90-spiritviews.conf
```

Elle attend uniquement que `ens3` soit routable, avec un timeout de 30
secondes. Le demarrage valide du 27 aout a termine cette attente en environ une
seconde, sans unite systemd en echec.

Les alertes Netdata locales sont installees dans :

```text
/etc/netdata/health.d/spiritviews.conf
/etc/netdata/go.d/httpcheck.conf
```

Elles couvrent les endpoints n8n/RustDesk, le CPU iowait (warning 20 %, critique
50 %), les latences de lecture/ecriture du disque `sda` (warning 20 ms,
critique 50 ms), son backlog (warning 5000 ms, critique 30000 ms) et la presence
des quatre conteneurs attendus. Les alertes Netdata standard restent actives
pour la memoire, l'espace disque et la sante Docker. La sonde RustDesk locale
utilise le port Caddy 22114 car le trafic emis localement ne traverse pas la
redirection publique PREROUTING 21114 vers 22114.
